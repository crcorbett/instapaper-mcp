# Repository instructions

Start at `docs/README.md` and load only the current semantic owners for the task.
Use the shared plugin described below; keep repository-specific skills local. `ARCHITECTURE.md` routes
stable boundaries; product specs own intent, active plans own work state,
runbooks own repeatable operations, and proof packets own claim evidence. Keep
the repository-specific harness facts in
`docs/governance/harness-profile.json`; use structured records under
`docs/audits/` for whole-repository audits. Complete the active bootstrap
harness plan before claiming the rendered defaults are qualified. Keep
Effects lazy, flat, sequential, and app-executed. Decode at ingress and encode
at outward boundaries. Avoid generic client callbacks, raw semantic identifiers,
primitive semantic config, unchecked output, runtime type-class branching,
pass-through helpers, giant routes, and service-aware presentation leaves. Edit
affected docs in the owning slice and run `bun run verification` before handoff.

## Shared development skills

Before starting work, follow [the plugin lookup](docs/skills.md) and load the
latest published Commonplace `development-workflows` plugin. Do not use saved
repository copies or assume a cached plugin version is current. Read the local
profiles in `docs/skill-profiles/` alongside the plugin.
